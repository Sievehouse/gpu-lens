# GPU Lens — Phase 1 Research Report: GPU Fleet Reliability and Capacity Intelligence

> **Epistemic Discipline Notice**: Throughout this report, claims are explicitly tagged as **[Documented Fact]** (backed by cited primary documentation or peer-reviewed operational papers), **[Engineering Inference]** (derived logically from documented system behaviors), or **[Assumption to Validate]** (operational hypotheses that depend on a specific operator's cluster topology or workload mix).

---

## 1. Operational Problems Addressed by GPU Lens

Operating Kubernetes clusters with NVIDIA data center GPUs introduces failure modes and capacity blind spots that differ qualitatively from CPU-only infrastructure:

1. **Fragmented Multi-Signal Triage During Job Failures and Stalls**:
   - **[Documented Fact]** In large-scale AI training clusters, hardware failures are rare by job count (<1% of jobs) yet disproportionately impact total GPU runtime (18.7% of GPU runtime in Meta FAIR's 11-month study across 16,000-GPU and 8,000-GPU NVIDIA A100 clusters spanning 4 million jobs and >150M GPU-hours) ([Revisiting Reliability in Large-Scale Machine Learning Research Clusters, arXiv:2410.21680v2](https://www.google.com/search?q=https%3A%2F%2Farxiv.org%2Fhtml%2F2410.21680v2)).
   - **[Documented Fact]** Failure symptoms in distributed GPU workloads are noisy and span multiple failure domains: an application exit or `NCCL Timeout` can stem from user code bugs, deadlocks, data-loading stalls, or underlying hardware faults on a peer rank (such as PCIe link errors, XID 79 "GPU has fallen off the bus", uncorrectable ECC double-bit errors, row-remap failures, or NVLink CRC/replay errors) ([arXiv:2410.21680v2, Section II-E \& Table I](https://www.google.com/search?q=https%3A%2F%2Farxiv.org%2Fhtml%2F2410.21680v2)).
   - **[Documented Fact]** When a GPU device fails at runtime, the Kubernetes device plugin notifies the kubelet via `ListAndWatchResponse`, which decrements the node's `status.allocatable["nvidia.com/gpu"]` count while `status.capacity["nvidia.com/gpu"]` remains unchanged. Crucially, pods already assigned to the failed device remain bound to it and typically enter `Failed` or `CrashLoopBackOff` states ([Kubernetes Device Plugins — Device plugin and unhealthy devices](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Fconcepts%2Fextend-kubernetes%2Fcompute-storage-net%2Fdevice-plugins%2F)).
   - **[Engineering Inference]** Because GPU hardware telemetry resides in Prometheus/DCGM Exporter while pod phase transitions, container exit codes, node conditions, and scheduler failures reside in the Kubernetes API, an on-call engineer investigating a crashed or pending job must manually correlate timestamps, node names, GPU UUIDs, and pod mappings across at least two separate systems.

2. **Opaque Pending GPU Workloads**:
   - **[Documented Fact]** Kubernetes GPUs are scheduled as integer extended resources (`nvidia.com/gpu`) via device plugins and cannot be overcommitted ([Kubernetes Schedule GPUs](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Ftasks%2Fmanage-gpus%2Fscheduling-gpus%2F)). When a pod cannot be scheduled, `kube-scheduler` emits a `FailedScheduling` event (e.g., `0/N nodes are available: M Insufficient nvidia.com/gpu`, node affinity/selector mismatches, or node taints/unschedulable conditions) ([NVIDIA k8s-device-plugin Troubleshooting](https://www.google.com/search?q=https%3A%2F%2Fdocs.nvidia.com%2Fdatacenter%2Fcloud-native%2Fgpu-operator%2Flatest%2Ftroubleshooting.html)).
   - **[Engineering Inference]** Standard cluster dashboards show aggregate GPU count, which hides *why* a multi-GPU pod is pending—for example, when cluster-wide free GPUs exceed the pod's request, but those GPUs are fragmented across nodes, or when a node's `allocatable` GPU count dropped below `capacity` due to an unhealthy device or cordoned node.

3. **Allocated GPUs with Persistently Low Compute Utilization**:
   - **[Documented Fact]** Under the Kubernetes device plugin model, once a pod is scheduled with `nvidia.com/gpu: N`, those physical GPUs (or MIG instances) are exclusively allocated to the container for the pod's entire Running lifecycle, regardless of actual compute utilization ([Kubernetes Device Plugins](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Fconcepts%2Fextend-kubernetes%2Fcompute-storage-net%2Fdevice-plugins%2F); [OpenCost Specification — Workload Costs](https://www.google.com/search?q=https%3A%2F%2Fopencost.io%2Fdocs%2Fspecification%2F)).
   - **[Documented Fact]** DCGM Exporter exposes `DCGM_FI_DEV_GPU_UTIL` (mapped to `DCGM_FI_DEV_GPU_UTIL_RATIO`, GPU utilization in %) and `DCGM_FI_DEV_MEM_COPY_UTIL` (memory copy utilization in %), alongside `DCGM_FI_DEV_FB_USED` (framebuffer memory used in MiB) ([NVIDIA DCGM Exporter Metrics Reference](https://www.google.com/search?q=https%3A%2F%2Fdocs.nvidia.com%2Fdatacenter%2Fdcgm%2Flatest%2Freference%2Fdcgm-exporter-metrics.html)).
   - **[Engineering Inference]** Persistently low `DCGM_FI_DEV_GPU_UTIL` over an extended allocation window DOES NOT automatically prove wasted capacity or an idle interactive notebook; it can also be caused by CPU/storage data-loader bottlenecks, network/NCCL synchronization stalls, checkpoint writes, or memory-capacity-bound inference workloads where framebuffer memory (`DCGM_FI_DEV_FB_USED`) is heavily utilized while SM compute utilization remains low. Operators need a transparent calculation of low-utilization GPU-hours paired with a structured diagnostic checklist rather than naive "waste" claims.

4. **Silent Monitoring Blind Spots and Uncorrelated Telemetry**:
   - **[Documented Fact]** Prometheus collects metrics via HTTP pull scraping ([Prometheus Overview](https://www.google.com/search?q=https%3A%2F%2Fprometheus.io%2Fdocs%2Fintroduction%2Foverview%2F)). DCGM Exporter attaches Kubernetes workload labels (`pod`, `namespace`, `container`) only when `--kubernetes` is enabled and the exporter can query the kubelet's privileged `PodResourcesLister` gRPC socket at `/var/lib/kubelet/pod-resources/kubelet.sock` ([Kubernetes Device Plugins — Monitoring device plugin resources](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Fconcepts%2Fextend-kubernetes%2Fcompute-storage-net%2Fdevice-plugins%2F); [NVIDIA DCGM Exporter Metrics Reference — Exporter Labels](https://www.google.com/search?q=https%3A%2F%2Fdocs.nvidia.com%2Fdatacenter%2Fdcgm%2Flatest%2Freference%2Fdcgm-exporter-metrics.html)).
   - **[Documented Fact]** If `kubelet` restarts and the exporter mounted the socket file instead of the `/var/lib/kubelet/pod-resources/` directory, the socket inode becomes stale and pod-to-GPU mapping fails ([Kubernetes Device Plugins](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Fconcepts%2Fextend-kubernetes%2Fcompute-storage-net%2Fdevice-plugins%2F)). Similarly, if `nv-hostengine` or `dcgm-exporter` hangs or stops being scraped, Prometheus series become stale or absent.
   - **[Engineering Inference]** If a monitoring dashboard treats "zero alerts firing" as "cluster healthy" when telemetry is stale or pod labels are missing from DCGM metrics, operators suffer a dangerous blind spot.

## 3. What Existing Systems Expose vs. What They Leave Unsolved

### What Existing Systems Expose (**[Documented Fact]**)
1. **Prometheus + DCGM Exporter** expose per-GPU time series labeled with `gpu`, `UUID` (or `uuid`), `pci_bus_id`, `device`, `modelName`, `hostname`, and—when kubelet `pod-resources` mapping is active—`pod`, `namespace`, and `container` ([DCGM Exporter Metrics Reference](https://www.google.com/search?q=https%3A%2F%2Fdocs.nvidia.com%2Fdatacenter%2Fdcgm%2Flatest%2Freference%2Fdcgm-exporter-metrics.html)).
2. **Kubernetes API (`v1.Node`, `v1.Pod`, `v1.Event`)** exposes:
   - Node `status.capacity["nvidia.com/gpu"]` vs. `status.allocatable["nvidia.com/gpu"]`, node `spec.unschedulable`, node taints, and node conditions (`Ready`, plus NPD conditions such as `GPUXIDErrors` or `NVLinkProblem`).
   - Pod `spec.containers[].resources.limits["nvidia.com/gpu"]` (and requests), `spec.nodeSelector`, `spec.affinity`, `spec.tolerations`, `status.phase`, `status.containerStatuses[].restartCount`, `lastState.terminated` (`exitCode`, `reason`, `startedAt`, `finishedAt`).
   - Scheduler and kubelet `Events` (`FailedScheduling`, `BackOff`, `NodeNotReady`, hardware warning events).

### What They Do Not Attempt to Solve (**[Engineering Inference]**)
- **Deterministic Cross-Layer Correlation**: Prometheus alerting rules evaluate metric expressions in isolation (e.g., `DCGM_FI_DEV_XID_ERRORS > 0`), while Kubernetes events exist as ephemeral API objects. Neither system automatically joins a pod's `CrashLoopBackOff` / non-zero exit timestamp with a preceding XID 79 / ECC DBE / NVLink CRC spike on the exact GPU allocated to that pod, while also checking whether contradicting evidence exists (e.g., `OOMKilled` exit code 137 or image pull failure with zero GPU hardware errors).
- **Evidence-Grounded Capacity vs. Utilization Triage**: Existing dashboards either display raw `DCGM_FI_DEV_GPU_UTIL` line graphs or label low utilization as "waste." They rarely cross-check SM utilization (`DCGM_FI_DEV_GPU_UTIL`) against memory copy utilization (`DCGM_FI_DEV_MEM_COPY_UTIL`) and framebuffer occupancy (`DCGM_FI_DEV_FB_USED`), nor do they explicitly flag when `pod`/`namespace` labels are missing from DCGM series so operators aren't misled by incomplete pod attribution.
- **Explicit Blind-Spot Auditing**: Standard dashboards silently omit series or show flatlines when a scrape target fails or drops Kubernetes pod labels, rather than raising an explicit monitoring-freshness incident that suppresses false "healthy" conclusions.

## 4. The Specific Gap Targeted by GPU Lens

**GPU Lens** targets a focused, defensible operational gap: **a self-hosted, strictly read-only, deterministic diagnostic and capacity intelligence layer** that sits *beside* Prometheus, DCGM Exporter, and the Kubernetes API.

Unlike [NVIDIA NVSentinel](https://docs.nvidia.com/nvsentinel/getting-started/overview/) (which is a cluster-wide fault-quarantine and node-remediation control plane backed by MongoDB/PostgreSQL and admission webhooks) and unlike [OpenCost](https://www.google.com/search?q=https%3A%2F%2Fopencost.io%2Fdocs%2Fspecification%2F) (which is a cloud billing and chargeback engine), **GPU Lens**:
1. **Correlates four read-only signal streams**—GPU telemetry (DCGM/Prometheus), Kubernetes Node state (`capacity` vs. `allocatable`, conditions, taints), Kubernetes Pod lifecycle/restarts, and Kubernetes Events—into deterministic, evidence-backed **Incident Reports**.
2. **Enforces epistemic honesty in every finding**:
   - Explicitly separates **Observed Facts** (verbatim events, metric samples, exit codes, timestamps) from **Possible Explanations** and **Contradicting Evidence**.
   - Refuses to guess scheduling causes when `FailedScheduling` events or node state are missing.
   - Refuses to equate low `DCGM_FI_DEV_GPU_UTIL` with "proven waste," instead reporting transparent low-utilization GPU-hours alongside workload context (framebuffer usage, memory copy activity) and a structured engineering follow-up checklist.
   - Treats missing, stale, or unmapped telemetry as a first-class operational blind spot rather than proof of healthy hardware.
3. **Operates with zero cluster mutation risk and zero external SaaS/AI dependencies**:
   - Uses strictly read-only API calls (`get`, `list`, `watch` on `pods`, `nodes`, `events`; HTTP `GET` on Prometheus/DCGM endpoints).
   - Runs 100% offline out-of-the-box with six deterministic, realistic cluster scenarios for reproducible evaluation, incident training, and CI testing.

## 6. Why a GPU Infrastructure Provider Would Find GPU Lens Useful

1. **Zero-Risk Adoption in Regulated or High-Uptime Clusters**: Because GPU Lens is strictly read-only, never executes commands on GPU hosts, never injects mutating admission webhooks, and never cordons/drains nodes automatically, platform teams can deploy it immediately in production clusters without risking accidental mass node quarantine or job preemption.
2. **Reduced Mean Time to Triage (MTTT) on Ambiguous Failures**: As documented in Meta FAIR's operational study ([arXiv:2410.21680v2](https://www.google.com/search?q=https%3A%2F%2Farxiv.org%2Fhtml%2F2410.21680v2)), differentiating hardware faults (XID, ECC DBE, NVLink, PCIe, thermal slowdown) from application-level crashes (`OOMKilled`, NCCL rank hangs) is the central daily challenge of operating multi-tenant GPU clusters. GPU Lens automates the evidence-gathering and differential checklist step.
3. **Honest Capacity Reporting When Pod Mapping Is Partial**: Many clusters have mix-and-match nodes where some `dcgm-exporter` instances lack `--kubernetes` pod labels or have stale `pod-resources` sockets. GPU Lens explicitly separates *node-level GPU utilization* from *pod-attributed GPU utilization* and refuses to fabricate per-job efficiency numbers when pod mapping is absent.
4. **Offline Reproducibility for Runbook Validation & Onboarding**: New SREs can explore all six canonical GPU cluster failure modes locally in seconds without needing access to an expensive production H100/A100 cluster.

## 7. Limitations and Assumptions That Must Be Validated

### Documented Limitations of This MVP
- **Single-Cluster Scope**: Evaluates one Kubernetes cluster and one Prometheus/DCGM telemetry pipeline per instance; multi-cluster federation (e.g., MultiKueue spans) is out of scope.
- **Integer Device Plugin Focus (Limited MIG / DRA Depth)**: Models full physical GPUs (`nvidia.com/gpu`) and basic label inspection; does not yet compute combinatorial MIG slice packing (`GPU_I_PROFILE` / `GPU_I_ID`) or Kubernetes Dynamic Resource Allocation (`ResourceClaim` / `ResourceSlice`) topology graphs ([Kubernetes Device Plugins](https://www.google.com/search?q=https%3A%2F%2Fkubernetes.io%2Fdocs%2Fconcepts%2Fextend-kubernetes%2Fcompute-storage-net%2Fdevice-plugins%2F)).
- **No Kernel Log (`dmesg`) or InfiniBand Fabric Scraper**: Relies on metrics exported via DCGM Exporter / Prometheus and Kubernetes API events/conditions (such as NPD conditions). If an InfiniBand link flaps or PCIe bus drops without surfacing in DCGM Exporter or Kubernetes Node conditions/events, GPU Lens will only see the resulting telemetry staleness or pod failure ([arXiv:2410.21680v2, Section III](https://www.google.com/search?q=https%3A%2F%2Farxiv.org%2Fhtml%2F2410.21680v2)).

### Assumptions That Must Be Validated in Target Environments (**[Assumption to Validate]**)
1. **Metric Availability by DCGM Exporter Config**: **[Documented Fact]** `DCGM_FI_DEV_THERMAL_VIOLATION`, `DCGM_FI_DEV_POWER_VIOLATION`, `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL`, `DCGM_FI_DEV_ECC_SBE_VOL_TOTAL`, `DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_COUNT_TOTAL`, and `DCGM_EXP_GPU_HEALTH_STATUS` are shipped as *commented optional rows* in the default DCGM Exporter CSV ([DCGM Exporter Metrics Reference — Shipped Optional Metrics](https://www.google.com/search?q=https%3A%2F%2Fdocs.nvidia.com%2Fdatacenter%2Fdcgm%2Flatest%2Freference%2Fdcgm-exporter-metrics.html)). **[Assumption to Validate]** Operators must either enable these optional rows in their `dcgm-exporter` collector CSV/ConfigMap or rely on the default-enabled metrics (`DCGM_FI_DEV_GPU_TEMP`, `DCGM_FI_DEV_POWER_USAGE`, `DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_MEM_COPY_UTIL`, `DCGM_FI_DEV_XID_ERRORS`, `DCGM_FI_DEV_PCIE_REPLAY_COUNTER`, `DCGM_FI_DEV_FB_USED`, `DCGM_FI_DEV_ROW_REMAP_FAILURE`). GPU Lens handles both cases gracefully by marking optional metrics as `unavailable_optional` rather than fabricating zero values.
2. **Clock Synchronization**: **[Assumption to Validate]** Correlating Prometheus sample timestamps with Kubernetes `Event` and `ContainerStateTerminated` timestamps assumes cluster nodes and the control plane run NTP/chrony with clock skew bounded within a few seconds.
3. **Kubelet PodResources Labeling**: **[Assumption to Validate]** Per-pod GPU utilization attribution requires `dcgm-exporter` to run with `--kubernetes` (emitting `pod`, `namespace`, `container` labels, or legacy `pod_name`, `pod_namespace`, `container_name` with `--use-old-namespace`). GPU Lens supports configurable label mappings for both conventions and explicitly flags unattributed GPU series when neither is present.
